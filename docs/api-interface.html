dbstim API map

The public interface of the dbstim Python package as it is today: what each object is, which calls go over the network, which stay on your computer, and what happens when a session is interrupted.

1Mental model

Every object is reached from the one before it. A Client creates or opens an Experiment; publishing it freezes which trials each subject sees, in which session and run. Presentation progress is stored on the server, never in local files.

dbstimuli.com owns

  • the video catalog and filterable metrics
  • experiments, publication and each subject's manifest
  • presentation progress, results and the session claim

dbstim does

  • validates arguments before sending them
  • verifies manifests and every video by SHA-256
  • keeps a per-user media cache
  • sends start, record and finish, resending safely

Your program owns

  • rendering: PGL, PsychoPy or any player
  • timing, responses and what goes in a result
  • saying whether a trial was shown to the end

2Shortest journey: create, select, download

This is the whole path from nothing to verified video files. It records no presentation progress, so it is safe to run in a notebook ahead of time.

import dbstim
from dbstim import MetricFilter

client = dbstim.connect()   # asks for your password
experiment = client.create_experiment(
    "Memory demo", subjects=5, trials_per_run=24,
    filters=[MetricFilter("duration_seconds", ">=", 10)],
)
experiment.publish()        # freeze assignments
session = experiment.subjects[0].sessions[0]
folder = session.download() # verified .mp4 files
  1. connect() asks for credentials, then signs in HTTP. The cookie lives only in memory; client.close() forgets it.
  2. create_experiment() checks every argument locally local, then samples videos and saves a draft HTTP. To reopen one, use client.experiment("Memory demo") HTTP or client.experiment(id="…") local.
  3. publish() freezes subjects, sessions, runs and trial order HTTP. Publishing again changes nothing.
  4. experiment.subjects fetches the published list once HTTP; subject.sessions needs no request local.
  5. session.download() fetches each video not yet verified HTTP disk and returns the folder's Path. A second call downloads nothing.

The files are named by trial (trial-000001.mp4) with a .json receipt beside each. To learn which trial is which video, role or segment, use the Trial objects from run.trials; the folder holds no manifest of its own.

3Tracked presentation

A separate lifecycle, used inside your presentation program. Each trial is reported twice: once when it starts and once with its ending. The server, not dbstim, decides what comes next.

with session:  # start() now, finish() at the end
    while (run := session.next_run()) is not None:
        while (trial := run.next_trial()) is not None:
            path = run.media(trial)    # verified file
            run.record(trial, "started")
            result = present(path)     # yours
            run.record(trial, "completed", result=result)
  1. with session: calls start() HTTP, claiming the session for this Session object.
  2. next_run() and next_trial() each read progress from the server HTTP. They return None when nothing is left.
  3. run.media(trial) returns a verified file disk. After download() it makes no request; otherwise it downloads that one video first.
  4. record(trial, "started") HTTP must come before you present.
  5. present(path) is entirely yours: dbstim never opens a window, plays audio or times frames.
  6. record(trial, "completed", result=…) HTTP, or "abandoned" if it was not shown to the end.
  7. Leaving the block reads progress, then calls finish(status) HTTP.

4Trial and session outcomes

How with session: finishes

The block ends because…Status sent to finish()Then
it ran to the end and every trial is completed"completed"session done
it ran to the end but a trial is abandoned or unfinished"interrupted"progress kept; resume later
Ctrl-C (KeyboardInterrupt) or another non-Exception"interrupted"the interrupt is re-raised
an exception was raised inside it"failed"the original exception is re-raised; a finish failure is added as a note

Without a with block, call session.start() and session.finish(status) yourself; status is "completed", "interrupted" or "failed". session.results lists the results you sent, each with its status; session.abandoned lists abandoned trials, with or without a result.

5Recovery

Recovery always starts from what the server recorded. Nothing is replayed automatically.

Stopped mid-trial

run.next_trial() raises ApiError naming the trial, run and position. Decide what really happened, record it, then continue:

with session:
    for trial in session.unconfirmed:
        session.record(trial, "abandoned")
    while (run := session.next_run()) is not None:
        ...  # the usual loop

Record "completed" only if the participant saw it to the end.

Dropped connection

start, finish and record are resent unchanged up to three times (after 0.5, 1 and 2 s) on a connection failure or HTTP 500, 502, 503, 504. A 4xx answer is never resent.

If every attempt fails, that call stays pending: progress reads and other commands raise until you repeat the same call on the same Session object.

Another presenter owns this session

start() fails with HTTP 409 while another program holds the claim. Once you are sure it has stopped:

session.start(takeover=True)
with session:
    ...

Never take over a session another computer is still presenting.

Local media problems

A cached file whose size, hash or identity no longer matches its receipt is refused, not replaced. Symlinks are refused. Disk errors are raised as OSError, not as connection errors; drives that cannot hard-link (exFAT, FAT) need session.download(directory) on another disk.

Signed out (a later HTTP 401)? Call dbstim.connect() again. Recording "abandoned" needs a server with abandoned outcomes; an older server refuses it and the trial stays unconfirmed. More detail: Recovering a session.

Where files go

By default every program shares one per-user cache, so a notebook's download serves a presentation program started from any folder:

$XDG_CACHE_HOME/dbstimor ~/.cache/dbstim /{origin}server URL hash /{experiment}/{subject} /{manifest}SHA-256 /{session} /trial-000001.mp4 + .jsonvideo + receipt
  • Verified on arrival: type video/mp4, declared size (at most 4 GiB) and the server's SHA-256, written to a temporary file and hard-linked into place so no file is ever overwritten.
  • Verified on every use: run.media() re-hashes a cached file against its receipt before returning it, so it costs a read of the file even with no request.
  • Another folder: session.download(directory) or subject.session(id, directory=…). A later program must pass the same directory to find those files.
  • Deleting files never changes server progress, and downloading never records any.

8Boundaries

Not part of dbstim

  • Rendering, display timing or input handling.
  • Judging whether a trial was seen: you say so with record().
  • A manifest file for using the videos without dbstim objects.
  • Recording progress while offline: every command needs the server.

Good to know

  • Synchronous; a Client and its objects are not thread-safe.
  • Video is the only media type.
  • Only start, record and finish are resent automatically; creating, publishing and reads are not.
  • Python 3.11+, no runtime dependencies.
