Using the dbstim Python API

dbstim is a zero-dependency Python 3.11+ client for creating experiments on dbstimuli.com, caching SHA-256-verified stimulus videos on disk, and recording trial-by-trial presentation progress from your own task program.

Your Task Program Owns Rendering PGL, PsychoPy, or your custom player controls windowing, frame timing, stimulus playback, and response collection.
The Server Owns Assignments & State Publishing freezes subject/session/run manifests. Progress (started, completed, abandoned) is stored on the server.
Shared Verified Local Cache Videos downloaded in a setup script or notebook are verified into ~/.cache/dbstim and reused by task scripts in any folder.
Interactive Interface Map & Offline Reference Explore the object hierarchy and call flows in the API Interface Visualization (HTML) or download the Markdown API reference (api-interface.md). Every code snippet on this page is static documentation verified against local test fixtures—opening this page never contacts dbstimuli.com, creates experiments, or downloads study media.

1. Installation (From GitHub Release Tag)

dbstim requires Python 3.11+ and uses only the Python standard library at runtime. It is distributed directly from its GitHub repository rather than PyPI—always install from a pinned release tag (currently v0.5.0) or commit SHA so your study environment stays reproducible. 

# Install with pip from the v0.5.0 release tag
pip install "git+https://github.com/lobennett/dbstim.git@v0.5.0"

# Or add to a uv project
uv add "dbstim @ git+https://github.com/lobennett/dbstim.git@v0.5.0"

# Optional: include JupyterLab (>=4,<5) for the notebooks/api.ipynb walkthrough
pip install "dbstim[jupyter] @ git+https://github.com/lobennett/dbstim.git@v0.5.0"

Note: The legacy dbp_api package (revision d11933f) is superseded by dbstim. No Google Cloud SDK, service account key, or separate API token is needed; you sign in with your normal dbstimuli.com account.

2. Connection & Configuration

Use dbstim.connect() for interactive sessions (such as Jupyter notebooks or operator terminals). It prompts for your username if omitted and reads your password via getpass without echoing it to the screen: 

import dbstim

# Prompts for "dbstimuli.com username: " and hidden password
client = dbstim.connect()

# Or supply a username placeholder and prompt only for the password
client = dbstim.connect("your_username")

For non-interactive scripts or custom server targets, instantiate Client directly using placeholder values or environment variables (never commit real passwords to source control): 

from dbstim import Client

with Client(
    "your_username",
    "your_password",
    # Default origin is https://dbstimuli.com (HTTP allowed only for localhost)
    url="https://dbstimuli.com",
    timeout=120,  # per-request socket timeout in seconds (default: 120)
) as client:
    print(client)  # <Client your_username at https://dbstimuli.com>
  • In-memory credentials only: Session cookies and the CSRF token stay in memory on the Client instance and are cleared immediately by client.close(), exiting a with client: block, or an HTTP 401 response.
  • Strict origin safety: Remote origins must use https:// without embedded credentials, paths, queries, or fragments, and the HTTP transport never follows redirects.

3. Metric Discovery & Filtering

Call client.metrics() to inspect the catalog metrics you can filter on when designing an experiment. Each item is a frozen Metric(id, label, kind, unit, operators) object whose repr displays its human-readable comparison symbols: 

from dbstim import MetricFilter

metrics = client.metrics()
for metric in metrics:
    print(repr(metric))
# Example output:
# <Metric duration_seconds: Duration (number, seconds); operators > >=>

filters = [
    MetricFilter("duration_seconds", ">=", 10),
    MetricFilter("duration_seconds", "<=", 20),
    MetricFilter("audio_track_present", "==", True),
]
  • Definitions, not per-clip rows: client.metrics() lists metric definitions and allowed operators; actual filtering happens server-side against the published SQLite metric index when you create an experiment.
  • Operators: Numeric metrics accept ">=", "<=", ">", "<", "==" (or server codes "gte", "lte", "gt", "lt", "eq"). Boolean (True/False) metrics accept "==" and "!=" (mapped to "is" and "is_not"; "!=" is restricted to booleans).
  • Intersection semantics: Multiple MetricFilter entries combine with logical AND. Clips with unknown (NULL) values fail active comparisons.
  • Text search: create_experiment(..., content="...", corpus="both") searches clip text across "captions", "transcripts", or "both".

4. Creating, Publishing & Reopening Experiments

Creating a draft and publishing

client.create_experiment(...) validates your design counts locally, queries the server to pin the current catalog version, and saves a draft experiment. Calling experiment.publish() freezes every subject's session, run, and trial assignments into a SHA-256-verified manifest: 

experiment = client.create_experiment(
    "Memory demo",
    subjects=5,
    sessions_per_subject=1,
    runs_per_session=2,
    trials_per_run=24,
    foils_per_run=4,
    repeats_per_run=0,
    shared_fraction=0.1,
    seed=1,
    sampling="random",  # "random", "balanced", or "unique" YouTube channel sampling
    filters=[
        MetricFilter("duration_seconds", ">=", 10),
        MetricFilter("duration_seconds", "<=", 20),
    ],
    content="",
    corpus="both",      # "captions", "transcripts", or "both"
)

# Publish to freeze subject/session/run manifests before accessing experiment.subjects
experiment.publish()
summary = experiment.summary()
print(summary["id"], summary["published"], summary["shared_fraction_realized"])
  • Trial composition per run: Foils (second halves of split parent videos) and repeats count toward trials_per_run. Every run has parents = trials_per_run - foils_per_run - repeats_per_run initial parent presentations (requiring parents >= 1 and max(foils_per_run, repeats_per_run) <= parents), consisting of trials_per_run - 2*foils_per_run - repeats_per_run full videos, foils_per_run first halves, foils_per_run complementary second-half foils, and repeats_per_run repeats.
  • Scale limits: Up to 100 subjects and 50,000 total presentations (subjects * sessions_per_subject * runs_per_session * trials_per_run).
  • Shared fraction rounding: shared_fraction (0 to 1) sets the share of parent videos every subject sees, rounded down to whole videos. If rounding changes the share, create_experiment issues a UserWarning and experiment.summary()["shared_fraction_realized"] reports the exact realized fraction.
  • Publication requirement: Accessing experiment.subjects on an unpublished draft raises ApiError("Publish the experiment before choosing subjects").

Reopening an existing experiment

Each call to create_experiment(...) creates a new experiment record on the server even if the name was used before. client.experiment(name) opens the unique match (preferring its latest published revision), or raises a ValueError listing all matching revision IDs and creation timestamps so you can disambiguate with id=: 

# List all experiments owned by your account
all_experiments = client.experiments()

# Reopen by exact name when unambiguous
experiment = client.experiment("Memory demo")

# Or reopen a specific revision ID directly (required if multiple experiments share a name)
experiment = client.experiment(id="experiment-1")

5. Two Separate Journeys: Media Download vs. Tracked Presentation

dbstim separates fetching/previewing video files from running a tracked participant session. Pre-staging or previewing videos never claims a session or records participant progress on the server.

Journey A: Shortest Media-Download Path (Untracked)

Use session.download() in a setup script or notebook before the participant arrives. It downloads and verifies every MP4 in the session into your per-user cache (~/.cache/dbstim) without calling start() or modifying server progress: 

experiment = client.experiment("Memory demo")
session = experiment.subjects[0].sessions[0]

# Downloads & verifies all session MP4s into ~/.cache/dbstim
cache_folder = session.download()

# Preview or inspect a file path without starting the session
run = session.next_run()
if run is not None:
    first_mp4 = run.media(run.trials[0], mode="local")
  • Shared across directories: Because the default cache lives under $XDG_CACHE_HOME/dbstim or ~/.cache/dbstim (partitioned by origin hash, experiment ID, subject ID, manifest SHA-256, and session ID), a download from notebooks/api.ipynb is automatically reused by your task program running from any folder.
  • Custom folder: Pass session.download("/path/on/main/disk") or subject.session("session-001", directory="/path/on/main/disk"). A custom folder is used as given, so give each session its own folder. The target filesystem must support hard links (drives formatted as exFAT or FAT raise an OSError).

Journey B: Tracked Session / Run / Trial Loop

When presenting to a participant, enter with session: and iterate through session.next_run() and run.next_trial(). Your task function (present(path)) renders the video and returns a plain-JSON result dictionary: 

session = experiment.subjects[0].sessions[0]

with session:  # calls session.start(); finishes on exit
    while (run := session.next_run()) is not None:
        while (trial := run.next_trial()) is not None:
            path = run.media(trial)  # verified local Path
            run.record(trial, "started")
            result = present(path)   # your PGL / PsychoPy renderer
            run.record(trial, "completed", result=result)
  • Automatic session outcome: Exiting with session: calls session.finish(status) with "completed" when every trial in the session is "completed", "interrupted" if you stopped early (including Ctrl-C) or abandoned a trial, or "failed" if an exception was raised.
  • Download first for tight timing: The default run.media(trial) (mode="cache") downloads any file that is not cached yet, inside your loop. Call session.download() beforehand and use mode="local" to guarantee the loop never downloads.
  • Your code reports presentation: dbstim records whatever present(path) returns; it cannot observe the screen. With PGL, a play() call returning does not by itself prove the frames were displayed.
  • Pre-sliced segments: Every Trial has trial_id, stimulus_id, position (1-based within the run), role ("parent", "repeat", or "foil"), media_type="video", and segment (Segment(start_seconds, end_seconds) or None). Server-rendered halves and foils play from time zero of the downloaded MP4.

Media resolution modes (run.media(trial, mode=...))

  • mode="cache" (default): Returns the verified local Path if already in the cache (checking SHA-256, byte size, and manifest receipt), or downloads and verifies it on demand.
  • mode="local": Strictly offline check—returns the verified local Path if already downloaded, or immediately raises ApiError without making any network request. Ideal inside time-critical presentation loops after session.download().
  • mode="remote": Requests a temporary 5-minute streaming URL (https://dbstimuli.com/api/v1/media-access/...) from the server without writing to local disk.

6. HTTP vs. Local Operations & Timing Consequences

All network calls in dbstim are synchronous. Understanding which calls contact the server versus which inspect already-loaded memory or local disk lets you keep stimulus onset timing tight in PGL or PsychoPy.

Operation I/O Type What Happens & Timing Consequence
connect(), Client(...), client.metrics(), client.experiments(), client.experiment(...), client.create_experiment(...), experiment.publish(), experiment.summary() HTTP Synchronous HTTPS request(s) to dbstimuli.com. Call during experiment setup or startup, never during stimulus presentation.
experiment.subjects HTTP (1st) Local (cached) First access fetches the published experiment document containing all subject manifests; subsequent accesses on the same Experiment instance return the cached tuple immediately. (Calling experiment.subject(id) directly fetches .../manifest over HTTP.)
subject.sessions, subject.session(id), subject.session_ids, session.run_ids, session.run("run-001"), run.trials, trial.*, repr(...) Local (Memory) Zero network or disk I/O. Reads parsed, hash-verified manifest dataclasses already in memory.
session.download() HTTP + Disk Downloads any missing MP4s in the session and verifies SHA-256 checksums for all session files. Run before starting your task loop.
run.media(trial, mode="local")
(or mode="cache" after session.download())		 Local (Disk SHA-256) Zero network I/O. Hashes the local MP4 file with SHA-256 and checks its size and JSON receipt on disk. Call before trial onset to obtain the file path before flipping your first video frame.
run.media(trial, mode="remote") HTTP POST .../media-access to mint a 5-minute streaming URL.
session.next_run(), session.run("latest"), run.next_trial(), session.unconfirmed, session.abandoned, session.results, run.results HTTP GET Each call fetches current server session state (GET .../sessions/{id}) and verifies the manifest SHA-256. Call between trials, not inside a frame-rendering loop. Reads are not retried: a dropped connection raises ApiError, and leaving with session: on that exception finishes the session as "failed".
session.start(), session.finish(), run.record(...), session.record(...) HTTP POST (Retryable) Sends a deduplicated command to the server. On connection failure or HTTP 500/502/503/504, automatically retries up to 3 times with 0.5s, 1.0s, and 2.0s pauses (up to ~3.5s plus socket timeouts). Call immediately before/after presentation, outside your frame loop.

7. Recording Results & Honest Interruption / Recovery

Plain-JSON result validation

run.record(trial, status, result=...) validates result locally before sending any network request. result must be None or a plain JSON dict containing only str, int, float (finite only—no NaN or inf), bool, None, list, and dict. Convert NumPy scalars with int(x) or float(x), and use None when a participant gives no response: 

# Valid plain-JSON result payload (use int()/float() for numpy scalars, None for no response)
run.record(trial, "completed", result={"rt_ms": int(412), "choice": "left", "confidence": None})

# Read back server-recorded results at any time, including after all trials are finished
all_results = session.results
current_run_results = run.results

Resolving an interrupted (unconfirmed) trial

Every started trial ends in exactly one terminal state: "completed" (shown to the end) or "abandoned" (cut short by Ctrl-C, a crash, equipment trouble, or participant withdrawal). Neither is ever replayed automatically. If a program stops after record(trial, "started") without recording an ending, that trial is listed in session.unconfirmed and blocks run.next_trial() across the entire session until you resolve it: 

session = experiment.subjects[0].sessions[0]

with session:
    # Resolve any trial left unconfirmed by an earlier interruption:
    # Use "completed" ONLY if the participant actually saw the video to the end.
    for trial in session.unconfirmed:
        session.record(trial, "abandoned", result={"reason": "stopped mid-trial"})

    while (run := session.next_run()) is not None:
        while (trial := run.next_trial()) is not None:
            path = run.media(trial)
            run.record(trial, "started")
            result = present(path)
            run.record(trial, "completed", result=result)

# session.abandoned lists every abandoned Trial (even if recorded with result=None)
# session.results lists only trials where a non-None result dict was recorded
print(session.abandoned, session.results)
Sessions with abandoned trials finish as "interrupted" Because an abandoned trial was not completed, leaving with session: marks the session "interrupted" even after all remaining trials in every run have been presented. Calling session.finish("completed") on a session with abandoned trials is rejected by the server (HTTP 409).

Dropped connections & bounded command retries

start(), finish(), and record() attach a unique request_id and writer_id. If a connection drops or the server returns HTTP 500, 502, 503, or 504, dbstim resends the exact same payload up to 3 times (pausing 0.5s, 1.0s, and 2.0s). The server deduplicates by request_id, so a trial or session event is never recorded twice. Client errors (4xx) are never retried.

If all 4 attempts fail, dbstim keeps that command pending on the Session instance and blocks next_run(), next_trial(), and finish() until you repeat that exact same call on the same session / run object.

Taking over from a crashed presenter

If a previous task process crashed before exiting with session:, its presenter claim remains active on the server and a new session.start() raises ApiError (HTTP 409: Another presenter owns this session). Once you have verified that the previous program is no longer running, claim the session explicitly with takeover=True: 

# Only after confirming the previous task process has stopped:
session.start(takeover=True)
with session:
    for trial in session.unconfirmed:
        session.record(trial, "abandoned", result={"reason": "previous process crashed"})
    while (run := session.next_run()) is not None:
        while (trial := run.next_trial()) is not None:
            path = run.media(trial)
            run.record(trial, "started")
            result = present(path)
            run.record(trial, "completed", result=result)

8. Current Scope, Upgrading & Verification Limitations

  • Live server-backed progress (no offline event sync or portable export bundles): dbstim caches video files locally in ~/.cache/dbstim, but experiment creation, session claims (start/finish), progress queries (next_run/next_trial), and trial event recording (record) always communicate with the server over HTTPS. Offline event queuing/synchronization and standalone portable experiment exports are not implemented.
  • Server requirement for "abandoned" trial outcomes: Recording session.record(trial, "abandoned") requires the server to run dbp-dataset-browser revision 492a894 or later with its abandoned-outcomes database migration applied. If a deployed server predates that upgrade, calling record(trial, "abandoned") raises ApiError (HTTP 400: ... This server may predate abandoned trials; ask its operator to upgrade it) and leaves the trial unconfirmed without changing server state.
  • Upgrading from dbstim 0.4 to 0.5: dbstim 0.4 stored downloaded media in a working-directory .dbstim folder and could not advance past an abandoned trial. Version 0.5 uses the shared per-user cache (~/.cache/dbstim) and ignores old .dbstim folders (which you can delete when convenient).
  • Verification evidence boundary: All examples and behaviors documented in this guide are verified against the dbstim v0.5.0 source and local HTTP test fixtures (tests/test_dstim.py, tests/test_usability.py, tests/test_models_and_cache.py, tests/test_transport.py). Automated tests do not create experiments or mutate state on the live dbstimuli.com production server; live server feature availability depends on the operator's currently deployed server revision and database state.
